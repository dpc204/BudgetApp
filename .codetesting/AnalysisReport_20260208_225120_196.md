- **Confidence**: High
- **Test File**: Budget.ApiTests\Features\Authentication\JwtTokenServiceTests.cs
- **Bug Location**: Budget.Api\Features\Authentication\JwtTokenService.cs@37-44

### Analysis
The error 'IDX12401: Expires must be after NotBefore' occurs because the JWT library requires the expires time to be strictly AFTER the notBefore time, not equal to it. In the production code (JwtTokenService.cs), line 37 calculates 'expires = DateTime.UtcNow.AddMinutes(_opt.ExpMinutes)' and line 43 sets 'notBefore: DateTime.UtcNow'. When ExpMinutes is 0, both times can be equal (or expires can even be slightly before notBefore due to time progression between the two DateTime.UtcNow calls on lines 37 and 43). The production code needs to be fixed to either: (1) capture DateTime.UtcNow once and reuse it, ensuring expires is always after notBefore, or (2) add a minimum validity period when ExpMinutes is 0 or very small. The test correctly validates the edge case of ExpMinutes=0, expecting the token to expire at approximately the current time, which is a reasonable requirement.

### Suggested Fix
The CreateToken method in JwtTokenService.cs needs to be fixed to capture the current time once and ensure expires is always after notBefore. The recommended fix is to modify lines 37-44:

```csharp

// Ensure expires is always after notBefore (JWT spec requirement)

{
    expires = now.AddSeconds(1);
}

    issuer: _opt.Issuer,
    audience: _opt.Audience,
    claims: claims,
```

This ensures: (1) Both notBefore and expires calculations use the same base time, eliminating timing inconsistencies, and (2) When ExpMinutes is 0 or negative, the token gets a minimum 1-second validity period to satisfy JWT library requirements.
